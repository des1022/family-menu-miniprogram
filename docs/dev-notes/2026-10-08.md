## 修复 · 示例菜库填入失败（真机反馈）

**现象**：真机上点「填入示例菜库」→ 提示「填入失败，请重试」，一道菜都没进去。

**定位**：原实现有三个叠加的脆弱点，任何一个都能让整批无声失败：

1. `db.addDishes` 用 `Promise.all` 并发打 12 条 add。小程序端对云数据库的并发写有限制，
   且 `Promise.all` 只要一条 reject 就整批 reject —— 表现就是「一道都没进去」。
2. `db.addCategory(...)` 没有 catch。若 `categories` 集合缺失或权限不对，这一步直接抛错，
   **后面的菜品写入完全不会执行**。
3. catch 里只 `toast('填入失败，请重试')`，把真实的 `errCode / errMsg` 吞掉了。
   手机上没有控制台，等于完全没法定位。

**修复**：

- `utils/db.js`：`addDishes` 改为**顺序写入**，每 4 条 `sleep(200ms)` 避开频率限制；
  单条失败只记录不中断，返回 `{ ok, failed:[{name, err}] }`。`addDish` 补默认 `image:''` / `price:0`。
- `pages/tonight/tonight.js` `onSeed` 重写：
  - 分类逐个 `catch`，失败只 warn，**不再阻断菜品写入**
  - 先读已有菜名，**跳过同名菜**（重复点「填入」不会变成两份）
  - 带进度提示「正在填入 n/12」
  - 失败时 `wx.showModal` **把真实错误码显示出来**（部分失败显示前 3 条原因）
- `utils/util.js`：新增 `sleep(ms)` 与 `errText(e)`（把云开发错误翻译成人话 +
  给出「集合没建 / 权限不对 / 网络超时」的方向提示）。
- 新增 `db.pingAllCollections()` + 家庭页「**数据连接自检**」入口：
  逐个集合试读，直接在手机上列出哪个集合缺、什么错误码。以后这类问题不必再猜。
- 顺手：`onExport` 的四个读取加 `.catch(() => [])`（一个集合有问题不再让整份备份失败），
  并把 `shopping` 也纳入备份。

**教训**：批量写一律顺序化 + 单条容错；catch 里**不要吞掉 errCode/errMsg**；
本机没有微信开发者工具时，要在 App 内留一个能自己报错的诊断入口。

## 修复 · 云环境是空的（真机反馈，全部 5 个集合都不存在）

**现象**：上一条修复后弹窗给出了真实错误码 —— 12 道菜全部 `[-502005] Db or Table not exist: dishes`；
「数据连接自检」显示 **5 个集合全部不存在**（dishes / categories / records / members / shopping）。
所以不是代码问题：环境存在、可访问，但里面一张表都没有。

**已核对**：`utils/config.js` 的 `ENV_ID` 从未被改过（批一未触碰该文件，`git log -p -S"cloudbase-"` 全history只有一个环境 ID）。
说明是环境侧的问题（环境被重建 / 集合被删 / 指向了一个空环境）。

**关键知识（写下来免得再查）**：
- `Database.createCollection()` **仅支持云函数端**，小程序端不能建集合（官方文档明确标注「支持端：云函数」）。
  所以 App 内**无法自动建表** —— 只能控制台建，或走服务端通道。
- 服务端通道有两条：
  1. `POST https://api.weixin.qq.com/tcb/databasecollectionadd?access_token=...`（微信云开发 HTTP API，
     需要 AppSecret 换 access_token，可在 CI 里跑）；
  2. 云函数里 `db.createCollection(name)`（需要部署云函数）。
- 因此「集合不存在」的正确做法是**自愈 + 引导**：客户端检测到就明确告诉用户建哪几个。

**修复**：
- `utils/util.js` `errText` 重写：错误码 → 一句人话（`-502005` → 「集合还没建 —— 去云开发控制台新建，
  权限设『所有用户可读写』」）。原来把一整段英文文档链接糊在弹窗里，手机上根本没法读。
- `utils/db.js` 新增 `checkEnv()`（基于 `pingAllCollections`，返回 `{ready, missing, items}`），
  每项带 `raw`（真实集合名，给用户看/复制用）。
- `pages/tonight` 新增「云环境还没初始化」引导卡（`env.checked && !env.ready` 时显示）：
  逐条列出 5 个集合名 + 中文名 + ✓/✕、「复制集合名」、「重新检查」、
  以及 5 步操作指引（手机上用「云开发 CloudBase」小程序即可建集合）。
  同时 `loadAll` 先自检，环境不可用时**直接跳过所有查询**，不再打一堆注定失败的请求；
  未点/已点两块内容改为 `env.ready` 时才渲染，避免用户对着空页面猜。
- 用无头 Chrome 把引导卡在浅色/深色两套主题下都渲染自检过，布局成立。

**待办**：若希望「换环境/新环境一键建表」，需要 AppSecret（或云开发 API Key）
才能在 GitHub Actions 里调 `databasecollectionadd`。用户尚未提供，暂未做。

## 工具 · 云环境初始化（`tools/init-env.mjs` + `init-env.yml`）

**背景**：环境里的 5 个集合全被清掉了（见上一条），而重建非常繁琐。所以做成脚本：

- `tools/init-env.mjs`：用 AppID + AppSecret 换 access_token →
  `tcb/databasecollectionget` 查现有集合 → `tcb/databasecollectionadd` 建缺的 → 再查一遍复核。
  零依赖（Node 18+ 自带 fetch），ENV_ID 直接从 `utils/config.js` 读，不重复维护。
- `.github/workflows/init-env.yml`：手动触发，缺 `MP_APPSECRET` 时只告警不失败。
- `project.config.json` 的 `appid` 从占位符 `touristappid` 改成真实 AppID。

**重要结论（查证过官方接口清单，别再重复研究）**：

| 能力 | 能不能自动化 | 依据 |
|---|---|---|
| 新建 / 删除 / 查询集合 | ✅ 服务端 HTTP API | `POST api.weixin.qq.com/tcb/databasecollectionadd`，凭证 = 小程序 access_token（AppID+AppSecret） |
| 小程序端建集合 | ❌ | `Database.createCollection()` 官方标注「支持端：云函数」 |
| **修改集合权限 / 安全规则** | ❌ | 云开发 HTTP API 数据库章节只有 13 个接口（databaseadd / databaseaggregate / databasecollectionadd / databasecollectiondelete / databasecollectionget / databasecount / databasedelete / databasemigrateexport / databasemigrateimport / databasemigratequeryinfo / databasequery / databaseupdate / updateindex），**没有任何权限接口**；`dbmodifyacl` 只在第三方平台（`componenttcb` + component_access_token）开放 |

→ 所以「所有用户可读写」只能**在云开发控制台点**：
数据库 → 集合 → 权限 → 自定义安全规则 → `{"read": true, "write": true}`。

**顺带查清的一个知识点（很重要）**：
云开发的四种简易权限（`READONLY` 公有读私有写 / `PRIVATE` 仅创建者 / `ADMINWRITE` 仅管理端可写 / `ADMINONLY` 仅管理端）里，
**小程序端在任何一种下都不能写他人创建的数据**。而本项目需要「家人之间互相改对方的记录」
（买菜的人要能勾掉做饭的人加的采购项、任何人能撤掉别人点的菜），
所以**必须用自定义安全规则 `{"read": true, "write": true}`**，简易权限做不到 ——
这也解释了为什么当初会特意去设成「所有用户可读写」。

另一个相关坑：用自定义安全规则时，系统**不会**再自动给查询补
`_openid: '{openid}'` 条件，而且查询条件必须「覆盖」安全规则，否则报 `-502003 permission denied`。
`{"read": true, "write": true}` 恒真，所以不会踩这个坑（最省心的写法）。

**网络**：本机可直连 `api.weixin.qq.com`（0.27s 200），不需要代理。

## ✅ 最终解决：用 CloudBase MCP 自动设好了 5 个集合的权限

**结果**（`tools/cloudbase-perm.mjs` 跑完复核）：

| 集合 | 改前 | 改后 |
|---|---|---|
| dishes / categories / records / members / shopping | `PRIVATE`（仅创建者可读写） | `CUSTOM` + `{"read": true, "write": true}` |

`PRIVATE` 正是新建集合的默认值，也印证了原来的判断：不设权限的话，家人之间**互相看不到、改不了**，
而且不报错。

**怎么做到的**（关键情报，别再重新研究）：

1. 腾讯官方 npm 包 `@cloudbase/cloudbase-mcp`（stdio MCP server，42 个工具）。
   自己写一个迷你 MCP 客户端（spawn 子进程 + 换行分隔 JSON-RPC）即可调用。
2. `auth` 工具：`action=start_auth` + `authMode=device` → 返回
   `{user_code, verification_uri, expires_in:600}`；
   授权链接是 `https://tcb.cloud.tencent.com/dev#/cli-auth?user_code=XXXX&from=cli&flow=device`。
   `auth(action="status")` 的 `auth_status` 取值：`REQUIRED` → `PENDING` → `READY`。
3. 登录页有 **「使用微信公众平台账号登录」**（标注适用于小程序/小游戏/公众号网页）
   —— **不需要腾讯云账号、不需要实名认证**。这是绕开
   `console.cloud.tencent.com`（要注册+实名）的关键。
4. `auth(action=set_env, envId=...)` 绑定环境 →
   `managePermissions{action:'updateResourcePermission', resourceType:'noSqlDatabase',
   resourceId:'<集合>', permission:'CUSTOM', securityRule:'{"read": true, "write": true}'}`。

**踩坑**：
- 第一次脚本把 `auth_status` 的 `PENDING` 误判成"已授权"，于是在用户还没扫码时就往下跑，
  5 个集合全部返回「当前未登录」而跑空；正确的判定要写成「不等于 REQUIRED 且不等于 PENDING」。
- `@cloudbase/cloudbase-mcp` 的 device 流程里，MCP 进程**必须在用户授权期间存活**（它要换 token）。
  所以脚本要长驻轮询，不能起完就退。
- MCP 返回的 `verificationHint` 提示：对有后端权限控制的集合，
  前端 `.doc(id).update()/remove()` 不能只看有没有抛异常，
  要检查返回结果里的 `updated/deleted > 0`（以后排查可以借鉴）。

**沉淀**：新增 `tools/cloudbase-perm.mjs`（一句话搞定权限），
并把《环境初始化操作手册.html》从"必须人工去控制台点"改写为实际结论。

## 真机反馈修复 · 日历没有日期数字 + 分类管理点不进去

**① 日历里日期数字全不显示**（`pages/calendar/calendar.wxml`）

`wx:for="{{cells}}"` **没写 `wx:for-item="cell"`**，而正文用的是 `{{cell.day}}` / `wx:if="{{cell}}"`。
小程序循环变量默认叫 `item`，所以 `cell` 恒为 `undefined`：
`wx:if="{{cell}}"` 为假 → **整格内容都不渲染**，同时 `cell ? '' : 'cell--blank'` 还给每格加上了
`visibility: hidden`。结果就是「格子都在，但没有日期数字」。批一重写日历时引入的。

**② 家庭 → 分类管理点不进去**（`pages/category/category.js`）

`onLoad` 里还留着旧的「管理密码」门禁：
`if (!getApp().globalData.adminPwd) { toast('请先通过管理密码验证'); navigateBack() }`。
而这套门禁在批一重构时已经被整条去掉了（`app.js` 现在只有 `globalData: {}`），
所以 `adminPwd` 永远是 undefined → 一点进去就被弹回来。
`pages/admin/admin.js` 没有这个检查，所以「菜品管理」是好的 —— 这也解释了为什么只有分类管理不行。

**顺手加的防复发检查**（`tools/lint.py` 第 9 项）：
遍历所有 `wx:for`，若某个循环没声明 `wx:for-item`、而正文用到的根标识符
在页面 JS 里（连注释、字符串里）**根本找不到**，就报错。
实测：改坏 calendar.wxml 能立刻报出来，当前代码 0 误报。

**教训**：批量重构（尤其重写模板）时，"模板变量名"这类错误编译不报错、只能靠真机发现，

## 真机反馈修复 · 家里会多出「未命名」成员（成员身份被重复创建）

**现象**：家庭页出现 3 位成员 —— 一位叫「我」，两位空白「未命名」。用户反馈
「手机上登录多了一个，电脑上打开又多了一个」。

**云端取证**（CloudBase MCP 读 members）：

| 成员 | _openid 末 6 位 | 昵称 | 创建时间 |
|---|---|---|---|
| #1 | `RBP-Uw` | 我 | 14:55:30 |
| #2 | `whXc` | （空） | 17:43:35 |
| #3 | `whXc` | （空） | 17:48:06 |

而 dishes(12) / categories(4) / records(1) / shopping(4) **全部属于 `RBP-Uw`**，
`whXc` 名下没有任何业务数据。→ #2、#3 是同一个 openid 在 5 分钟内建出来的两条，
**确认是 bug，不是用户操作问题。**

**两个根因**：

1. **`getMyMember()` 把任何读失败都当成「记录没了」**
   `catch` 里无条件 `removeStorageSync(MEMBER_ID)`。于是网络/权限抖一下，
   「我是谁」的本地记忆就被清掉，紧接着 `ensureMyMember()` 发现没有本地记录 → 新建一条。
   → 表现就是「重新打开一次就多一个成员」。
   修复：只有 errCode `-502004` / 报错含 `not exist` 才清本地记忆；临时故障一律保留。

2. **`ensureMyMember()` 只要没有本地记录就静默新建**
   而本地记忆是**按客户端存的**（手机、电脑各一份），换端打开必然没有 → 必然新建。
   修复后的认定顺序：
   1. 本地记录还在 → 直接用
   2. 本地缓存过 openid → 按 openid 找回来（自动，不打扰）
   3. 家里一个人都没有 → 第一个使用者自动建（`self: 1`）
   4. 其余 → **返回 null，页面问「你是家里的哪位？」**，绝不静默新建

**配套改动**：

- `members` 新增 `self` 字段：`ensureMyMember/createSelfMember` 建的记 `self: 1`，
  手动添加（`addMember`，给家人预先建的那种）记 `self: 0`。
  `findSelfByOpenid` **只认 `self === 1`** —— 否则会把「你替爸爸手动加的那条」
  （它的 `_openid` 是你的）错认成你自己。
- 新增 `claimMember(id)`（指认已有成员）、`createSelfMember(count)`（新建「我」这条）。
  `createSelfMember` 建完会把文档读回来拿 `_openid`
  （客户端没有直接取 openid 的 API，只能从自己建的文档上读），
  若发现同一个 openid 早就认领过，就把刚建的删掉、用老的 —— 本地记忆丢失时自动合并，不产生重复。
- 新增 `components/who`（「你是家里的哪位？」弹层，自包含样式）：
  今晚页与家庭页在 `ensureMyMember()` 返回 null 时弹出；选完记住，之后不再问。
  弹层关掉后本次会话不再弹；家庭页成员区顶部留一行「还没认出你是哪位 · 点一下指认」。
- `removeMember` 移除的是自己时，连 `MEMBER_ID` 与 `MY_OPENID` 一起清掉，
  避免又被自动认回一条已删除的记录。

**数据修复**（CloudBase MCP）：`whXc` 名下两条重复成员已删除（无业务数据，删掉不影响任何记录），
给 `RBP-Uw` 那条打上 `self: 1`。现在 members 只剩 1 条。

**教训（值得长期遵守）**：
- 「按设备存的本地记忆」不能当成身份的唯一来源；一旦它丢了就新建记录，
  必然会在换端时产生重复数据。**身份这类东西要能在服务端认回来**（这里用 openid 兜底），
  认不回来就问用户，别猜、别自动建。
- `catch` 里清理本地状态前，一定先分辨「数据真的没了」和「这次没读到」。

## 真机反馈 · 详情弹层底部「加入今晚」看不见

用户截图：点开菜卡后弹层占满屏幕，**底部没有「编辑 / 加入今晚」**。

**根因**：`.dt-scroll`（详情弹层的 scroll-view）只有 `flex:1; min-height:0`。
微信的 `scroll-view` 在父级只有 `max-height`（`.sheet{max-height:86vh}`）而没有确定高度时，
不会收缩，而是被内容撑高 —— 这道菜有 3 步做法，内容一长，**底部那行按钮就被顶出屏幕**，
视觉上就是「没有加入今晚」。

**修法**（`pages/dishes/dishes.wxss`）：
- `.dt-scroll` 补 `max-height: 64vh` —— 内容超过就在弹层内部滚，按钮永远留在视野内。
- `.dt-actions` 补 `flex: 0 0 auto`，明确不参与压缩。上边距 34rpx → 24rpx。

**教训（第二次同类）**：弹层里的「主动作」不能依赖 flex 撑开 ——
**要么给滚动区一个明确的高度上限，要么把动作放在不参与滚动的固定区并显式声明不压缩。**
上一轮（菜卡点菜入口藏在弹层）和这一轮是同一个病根的两种表现：**关键动作的可见性没有兜底。**

**同类排查（同一个病根，主动全查了一遍）**：把项目里所有弹层内的滚动区高度都审计了一遍 ——
`hw-scroll`(56vh 做法) · `dec-list`(44vh 决策器) · `who-list`(52vh 身份指认) · `move-list`(50vh 分类移动)
· `dt-list`(52vh 日历当天) 都已有 `max-height`；只有 `dt-scroll` 漏了（本次修）。
另外**家庭页成员编辑弹层**（昵称 + 8 个口味胶囊 + 底部「移除/保存」）也是同一结构但没滚动区，
已补 `.fs-scroll`(56vh) 包住表单，`.fs-actions{flex:0 0 auto}` 保证按钮不被挤走。

  **sticky 的祖先链没有 overflow:hidden，所以吸顶是安全的**；右侧 `flex:1; min-width:0`。

### 2. 日历：点任意日期 → 安排那天吃什么（可提前排未来）

原来只有「有记录的日期」才能点开，且只能看 + 「再做一次」。现在：

- `calendar.js`：
  - `onDayTap` 改为**任何日期**都打开 `openArrange(date)`；
  - 弹层状态 `arr`：`title`（今天 / 补记 / **安排到** + 中文日期）、已排数量、
    搜索关键词、`tab`（全部菜 / ★常吃）、`items`（每行带 `on` 标记）、`canReuse`；
  - `togglePlan(dish)`：点行 = `addToTonight(dish, date)` / `removeFromTonight(date, dishId)` ——
    **数据层本来就支持任意日期**，所以「提前安排」不需要新的数据结构；
  - 已排的菜以胶囊横滑展示，点一下即可撤掉；「已排」排到列表最前面，方便反悔；
  - `lastText()`：每行显示「素菜 · 12 天没做了」，帮家里人避免连着重复吃；
  - 「加进今晚」保留（把某天的菜搬到今天），但**先二次确认**再 `clearDrafts`，不再静默覆盖今天的菜单；
  - 关掉弹层若有过改动才 `loadRecords()` 刷新色点。
- `calendar.wxml`：新增 `.arr-picked` / `.arr-search` / `.arr-tabs` / `.dt-list` 行 + `.ar-btn`（＋/✓）；
  底部固定「加进今晚 / 完成」；日历下方加一行提示「点任意日期，就能安排那天吃什么 —— 可以提前排未来几天」；
  空态文案也改成引导点日期。
- `calendar.wxss`：新增上述样式，`.arr-actions{flex:0 0 auto}`（沿用上一轮「按钮不能被挤走」的规矩）。
