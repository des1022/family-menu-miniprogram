# 开发笔记 2026-11-05

## 【严重】菜库只显示 20 道 —— 分页上限写错了

用户反馈：「上传了很多菜品，但是只显示 20 道，前面上传的又被后面上传的代替了」。

### 根因
`config.PAGE_SIZE = 100`，注释还写着「默认 20，最大 100」——**记反了**：
- **小程序端** `limit()` 最多 **20** 条；
- 云函数端才是 100。

于是 `limit(100)` 被 SDK 悄悄截成 20 条，而 `fetchAll` 的判断是
「返回条数 < 请求条数 → 认为拉完了」→ **第一页 20 条就 break**。
菜库按 `createTime desc` 排序，所以永远是**最新的 20 道**，
看起来就像「前面传的被后面传的顶掉了」——**数据一条都没丢**，只是没读出来。

顺带影响：`records` 也一样只读 20 条 → 日历历史、决策器的「近一月做过几次」、
采购清单的食材汇总，全都只基于最近 20 条记录。

### 修法（两处都堵）
- `config.PAGE_SIZE` → 20，注释改成「别改大」。
- `utils/cloud.js` 的 `fetchAll`：请求条数按 `CLIENT_PAGE_MAX = 20` 夹紧，
  翻页改成按**实际返回条数**推进（`skip += list.length`），空页直接 break，guard 放宽到 200 页。
  这样就算以后有人又把 PAGE_SIZE 写回 100，也不会再截断。

### 顺手修的两个同类坑
- `resolveCloudImages` 以前是 `need.slice(0, 50)` —— 云函数单次最多换 50 个，
  但第 51 张之后的菜图**永远换不到**，只能显示首字占位（看起来像「图丢了」）。改成每 50 个一批。
- `watchRecordsByDate` / `watchShopping` 的 watch 回调原来直接用 `snapshot.docs`；
  watch 也有 20 条上限，桌上/清单超过 20 条会少。改成「收到变化就重新查一次」。

### 已知的后续风险（这次没动）
修好之后 `getAllRecords()` 是**全量**读的（分页），记录攒到 200+ 条时，
菜库这一页会变成 10+ 次往返、 noticeably 变慢。真到那一步，把拉取挪进云函数（一次 100 条），
或者菜库只查最近 28 天的记录（它只用得着 freq / lastMap / 今天在不在桌上）。

## 菜多了会慢吗？—— 改成 count + 并发分页

用户 42 道菜之后问「继续传会不会再出问题、怎么彻底解决」。

**硬截断已经彻底没有了**（上一节的修法 + 这一节的兜底），但串行分页会让**速度**先顶不住：
42 道 = 3 次往返、300 道 = 15 次，每次 100~250ms，进菜库就开始等。

`utils/cloud.js` 的 `fetchAll` 现在：
1. 先 `count()` 拿总数（1 次往返）；
2. 按 `ceil(total/20)` 算页数，**每轮并发 4 页**（`FETCH_CONCURRENCY`，读并发贪多会偶尔超时）；
3. 按 `_id` 去重（排序时间并列时 skip 可能重复一条）；
4. `count` 失败 → 退回原来的串行分页，不会因为「数不出总数」就显示空。

粗略估算（每页 ~150ms）：42 道 1 轮、300 道 4 轮、1000 道 13 轮。
再往上才需要把读挪进云函数（服务端一次 100 条）或改用 `aggregate` 做统计 —— 现在没必要。

顺带记一下**下一个真正的瓶颈**（还没动）：`getAllRecords()` 是全量读的，
一天 2~4 条记录，一年就是 ~1000 条 → 菜库这页会多 13 轮。到那一步的做法：
菜库只查近 28 天（它只用得着 freq / lastMap / 今天在不在桌上），或者把统计改成
`aggregate().match().group()` 一次拿回「每道菜做过几次 + 上次做的日期」。

## 读数据挪进云函数（挂在 img-url 里，`action: 'query'`）

用户要求「现在就把读取移进云函数，以后我怕忘」——做了。

### 为什么没建成独立的 `db-fetch`
先按独立云函数写的，CI 一跑就报 `ResourceNotFound.Function`（未找到指定的Function）：
**`ci.cloud.uploadFunction()` 只能更新已存在的云函数，新建必须在云开发控制台点一次。**
不想让用户手动点点，于是把读集合挂到**已经部署的 `img-url`**（加 `action: 'query'` 分支），
名字虽然叫 img-url，注释里写清了它现在是「云端小工具」。哪天想拆出去：
控制台建好新函数 → 把 `queryCollection` 整段挪过去 → 客户端改函数名即可。

### 云函数这边
- 入参 `{ action:'query', collection, where?, orderBy?, skip?, limit? }`，**集合名白名单**
  （dishes/records/categories/members/shopping）。
- 服务端 limit 上限 100，自己翻页；单次最多 500 条 / 30 页（返回体别撑破 1MB），
  超了让客户端带 `skip` 再来。
- 不传 `action` 时行为完全不变（换图片链接），老调用方无感。

### 客户端 `utils/cloud.js`
- `fetchAll(name, opts)` 签名改了（原来 `(collFn, orderFn)`）：`opts = { where, orderBy }`，
  **8 个调用点全改**。
- 首选云函数；**不通就退回客户端分页**（count + 并发 4 页 + 串行兜底），
  并用 `fnBroken` 记住，本次会话不再反复试 —— 云函数没部署也只是慢一点，不会空、不会错。

### 部署
- `scripts/deploy-functions.js`：同一把小程序上传密钥 + `ci.cloud.uploadFunction()`，
  云环境 ID 从 `utils/config.js` 读，不新增 secret；**只列已存在的函数**。
- `deploy-mp.yml` 末尾 `Deploy cloud functions`，放在「上传版本 + 出二维码」之后：
  云函数失败不耽误发版。

### 现在的代价
- 菜品/记录走云函数：42 道 = **1 次调用**；1200 条记录 = 3 次（500/500/200）。
- 云函数冷启动约 200~500ms，热了之后 50~150ms；比原来客户端翻十几次强很多。
- 云函数超时/内存是控制台里配的（默认够用）；真觉得慢可以去调大超时。

### CI 上踩的两个坑（都修好了）
1. **`ci.cloud.uploadFunction()` 只能更新已存在的云函数**：新建的名字会报
   `ResourceNotFound.Function`。所以别指望 CI 建函数 —— 先在云开发控制台「云函数 → 新建」
   点一次，之后 CI 就能一直更新它（这也是读集合挂在 img-url 里的原因）。
2. **上传完 node 不退出**：`miniprogram-ci` 内部留着没关的 socket，日志已经打出
   `[fn] 全部完成`，但这一步还会一直挂着，直到 `timeout-minutes` 才报失败
   （第一次白等了 6 分钟）。脚本末尾必须 `process.exit(0)`。
   顺手给 workflow 的这一步加了 `timeout-minutes: 6`、整个 job 加了 20 分钟上限。

### 部署结果（2026-11-05 验证）
- 第 82 次构建 **success**，日志：`[fn] 上传 img-url … / img-url 完成 {"filesCount":2,...} / 全部完成`（20 秒）。
- 客户端这版（v1.0.82 预览码）第一次进菜库就会走云函数读集合；
  云函数冷启动 200~500ms、热了 50~150ms。
