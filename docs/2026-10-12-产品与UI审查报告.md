# 家庭菜单 · 产品与 UI 全面审查

日期：2026-10-12 · 版本基线 1.0.67

> ⚠️ **本报告有两处提案已被推翻，请看修正版**
> `docs/2026-10-12-现有功能全景与提案修正.md`
> —— 起因：本报告只读了字段名就推测缺口，导致「采购清单按超市动线分区」这类**已有功能**被当成缺口。
> 修正版逐页精读了实现，撤回了 3 条提案，并给出了更准确的证据。

**审查方法**：逐页读代码 + 量化统计（页面规模 / 交互入口 / 设计 token 使用 / 底色块分布 /
硬编码色 / 色相数值），并根据结果核对，**不是凭印象**。附图为《色板诊断》。

---

## 一、先给结论

1. **产品骨架比预期完整**。9 个页面 + 54 个数据函数，「点菜 → 排未来 → 采购 → 用完回顾」
   这条主闭环是通的，而且有几处是真的想清楚了（决策器、实时协作、数据自持）。
2. **有 3 处「半成品」**：成员忌口字段填了没人用、在家人数没接进决策器、菜品价格字段几乎闲置。
   这三处都是**数据已经在，就差最后一根线**，性价比最高。
3. **UI 的问题不是「不好看」，是「没有使用规则」**。色板本身协调（暖厨房调性），
   但一屏里同时亮 4–6 种浅底色，所以显得糊。**先定规则，颜色一个不改都能静下来。**
4. **深色主题有系统性隐患**：`--pri` 在深色下变纯白、`--pri-l + --pri-ink` 变成「白底 + 白字」，
   已经为此手工兜了 3 次（管理页编辑按钮 / 日历日期胶囊 / 有记录格）。需要机制性解决，不是再兜一次。
5. **有一处死代码**：`components/skeleton` 从未被使用，而且它的颜色是**冷灰** `#F2F3F5`，
   和全站暖灰 `#F4EFE9` 不同源 —— 哪天启用会立刻不搭。

## 二、产品设计审查

### 2.1 已经做得好、不用动的

| 项 | 为什么好 |
|---|---|
| 四段闭环 | 点菜（今晚）→ 排未来（日历）→ 采购（清单）→ 回顾（本月），每段都有明确出口 |
| 「帮我选一顿」决策器 | 按「搭配 / 人数 / 辣度」凑一桌 + 可单独换一道 —— 解决的是「不知道吃什么」这个真问题 |
| 实时协作 | `watchDishes / watchRecordsByDate / watchShopping`，家人勾掉的买菜项当场可见 |
| 数据自持 | 备份导出 / 恢复 + 自建云函数取图，数据在用户自己的环境里 |
| 新手引导 | 「云环境没初始化」直接给出 5 步图文；还有示例菜库一键填入 |
| 空态 | 四个页面统一用 `components/empty`，配场景图标（碗 / 菜篮 / 日历 / 盘子） |

### 2.2 功能缺口（按价值排序）

#### 🔴 P0 — 承诺了但没兑现

**① 成员「口味 / 忌口」填了没有人用**

- 证据：`members.tastes` 字段存在（`db.js` L225/L233/L332）；家庭页提示语写的是
  「点菜时会用到，比如『不吃香菜』」；但全站 **没有任何一处读取它**（grep `tastes` 只有
  成员表单的读写，决策器里的 `taste` 是另一个东西 —— 那是「辣度」选项）。
- 影响：用户认真填了忌口，决策器照样推荐撒香菜的菜。**这比"没有这个功能"更伤信任。**
- 方案（两步，可只做第一步）：
  1. 决策器候选池过滤：把忌口文本拆成关键词，命中「菜名 / 食材 / 标签」就跳过；
  2. 点菜和详情里加提示：「含香菜 · 程蒙不吃」。
- 改动量：中（决策器 `pickCandidate` + 菜库详情）

#### 🟠 P1 — 数据已经算好，就差接上

**②「今晚在家吃」的人数没接进决策器**

- 证据：`db.countEatTonight()` 已实现，家庭页显示「N 位成员 · 今晚 X 人在家吃」，
  今晚页也显示「X 人」；但决策器的「人数」是另外手选的 `SIZES`，两者互不相干。
- 影响：同一件事要填两遍；还可能互相矛盾（家里标了 3 人，决策器手选 5 人 → 菜量不对）。
- 方案：决策器默认选中「按在家人数」，标题显示「3 人（今天在家的）」，仍允许手改。
- 改动量：**小**（只改默认值 + 一行提示）

**③ 菜品「价格」字段几乎闲置**

- 证据：`dish.price` 只在菜品管理页出现（`manage-price`），菜库卡片 / 今晚 / 详情都不显示。
- 三个方向，需要你选：
  - **A（推荐）**：在采购清单用它估算「今天大概花多少」—— 让字段真的有用；
  - B：菜库卡片显示价格 —— 信息更全，但自己做菜场景意义不大；
  - C：**删掉这个字段** —— 减少录入负担（家庭菜单本来不需要记菜价）。
- 改动量：小

#### 🟡 P2 — 能力缺口（可做，但要权衡成本）

**④ 没有订阅消息提醒**（全站无 `requestSubscribeMessage`）

- 可用场景：下午 4 点提醒「今晚还没点菜」、买菜路上提醒「还有 3 项没买」、周末提醒补货。
- 代价：需要用户主动订阅 + 云函数定时触发（有额度成本）。
- 建议：先只做 1 个模板（今晚未点菜）验证有没有用，别一次铺开。

**⑤ 没有「吃完的反馈」**

现在只有「谁点的、什么时候吃的」，没有「好不好吃」。加一个轻量反馈
（这道菜还想再做 / 暂时不想了），可以：
- 让决策器的权重更准（不想做的降权）；
- 让「最近家里常吃」不再只是"次数最多"，而是"最受欢迎"。
- 改动量：中

**⑥ 采购清单没有按「超市动线」分区**

现在按菜品分组（这道菜的食材）+ 常备调料。买菜时的实际动线更关心
「蔬菜 / 肉蛋 / 粮油 / 日杂」。需要给食材打一级分类。
- 改动量：中（食材分类表 + 分组逻辑）

**⑦ 没有周视图 / 一周总览**

日历是月视图 + 「接下来的安排」列表，没有「这周 7 天各吃什么」的一屏。
- 判断：**优先级低** —— 「接下来的安排」已经覆盖了主要需求，加了反而重复。

### 2.3 信息架构的小问题

- **「菜品管理」藏在 家庭 → 管理 里**，但批量上架 / 改分类是偏高频的动作，
  而菜库页只有「新增」。可考虑在菜库页头加一个入口。
- **搜索覆盖不全**：菜库、日历有搜索；今晚页的「最近家里常吃」列表没有，菜多时要一路滚。

## 三、UI 设计审查

### 3.1 一致性 —— 这是最健康的一维

| 指标 | 现状 | 评价 |
|---|---|---|
| 主题绑定 | 9/9 个页面都绑了 `themeCls` | ✅ 完整 |
| 设计 token | 37 个变量；只有 1 个（`--r-lg`）从未被引用 | ✅ 覆盖高 |
| 硬编码色 | 全站 101 处，集中在 4 个文件（family 13 / calendar 5 / skeleton 3 / …） | ⚠️ 有残留但可控 |
| 组件复用 | 空态、确认弹窗、「你是哪位」都是组件 | ✅ |
| 卡片 / 圆角 / 阴影 / 间距 | 一套语言 | ✅ |

### 3.2 色块搭配（重点，详见附图）

**三个能指认的问题：**

| # | 问题 | 硬数据 |
|---|---|---|
| ① | **两个浅底色块几乎分不出** | `--pri-l` L95 vs `--acc-l` L93 —— **明度只差 2%**，色相差 22°，在白卡上是「两片几乎一样的米色」 |
| ② | **危险色和主色几乎同色** | `--pri` H15° vs `--danger` H5° —— **只差 10°**，都会被读成「橙红」 |
| ③ | **深色下主色变白** | `--pri` → `#FFFFFF`、`--pri-l` → `rgba(255,255,255,.16)`、`--pri-ink` → `#FFFFFF`，于是「白底 + 白字」 |

**底色块密度（一屏同时亮几盏灯）：**

| 页面 | 语义底色种数 |
|---|---|
| 日历 | **6 种** |
| 今晚 / 菜品管理 | **5 种** |
| 菜品编辑 / 菜库 | 4 种 |
| 采购清单 / 家庭 / 分类 / 海报 | **2 种** ✅ |

采购清单和家庭页那种「2 种」的克制，才是目标状态。

**建议（分成两步，第一步就能解决大部分观感问题）：**

**第一步 · 定用途规则（颜色一个不用改）**

| 颜色 | 只允许用于 | 明确不要用于 |
|---|---|---|
| 主色 / 主色浅底 | 主操作按钮、当前选中、今天 | 纯装饰、区块图标 |
| 强调 / 强调浅底 | **只给「时间与记录」**：有记录的日子、回顾数据、名次 | 状态、按钮、区块图标 |
| 成功 / 成功浅底 | **只给「已完成」**：已上架、已买、已确认 | 当装饰色 |
| 危险 | **只给破坏性动作，且只用文字色、不填底** | 任何填充色块 |
| 中性浅底 | 一切容器、分区、提示条、未选中 | — |

**第二步 · 可选的三处色值微调**

1. 危险色 `#C94A3F` → `#B03A34`（H5 L52 → H4 L46），和主色拉开明度层次；
2. 强调浅底 `#FCF3DF` → `#F8E8BC`（L93 → L86），从「几乎一样的米色」变成明确的奶油黄；
3. **新增一组跨主题恒暖变量**（`--warm / --warm-l / --warm-ink`），专给「不管深浅都要是暖色」
   的组件用 —— 从此不用每处手工兜深色（第 ③ 类问题一次性解决）。

### 3.3 该清理的残留

| 项 | 说明 |
|---|---|
| `components/skeleton` | **死代码**（无人引用），且色值 `#F2F3F5 / #E9EBEF` 是**冷灰**，与全站暖灰 `#F4EFE9` 不同源 → 删掉，或改成暖灰再用 |
| `--r-lg` | 37 个 token 里唯一从未被引用的 |
| `family.wxss` 13 处硬编码 | 其中 `#37776A` / `#2A5F54` 是**直接把深色主题的值写死了**（外观预览卡），应改成变量或注明是"预览色" |
| `#2A5F54`（calendar 3 / dishes 2 / shopping 2） | 都是「深色下今天格的字色」，属合理兜底，但抽成一个变量更干净 |

### 3.4 视觉层级

- 三个 tab 页的第一屏都是「标题 + 卡片流」，**缺一个视觉锚点**。
  唯一的例外是日历页刚加的暖色横幅 —— 它现在一眼就能抓住「这个月吃了 23 顿」。
- 建议：今晚页也给一个这样的锚（例如「今晚 3 道菜 · 2 人吃」的横幅），
  和日历形成同一套语言。

## 四、优先级路线图

| # | 事项 | 类型 | 改动量 | 价值 |
|---|---|---|---|---|
| 1 | 忌口字段接进决策器 | 产品 | 中 | **高**（兑现承诺） |
| 2 | 决策器默认用「在家人数」 | 产品 | 小 | **高** |
| 3 | 色板用途规则落地（改 3–4 处样式） | UI | 小 | **高** |
| 4 | 删死代码 + 清 family 硬编码 | UI | 小 | 中 |
| 5 | 价格字段决断（用 / 删） | 产品 | 小 | 中 |
| 6 | 主题变量补一组「恒暖色」 | UI | 小 | 中（机制性） |
| 7 | 订阅消息（1 个模板试水） | 产品 | 大 | 中 |
| 8 | 吃完的反馈 | 产品 | 中 | 中 |
| 9 | 采购按超市动线分区 | 产品 | 中 | 中 |
| 10 | 今晚页加视觉锚 | UI | 小 | 低 |
| — | 周视图 | 产品 | 中 | 低（不建议做） |

**建议的起步组合：1 + 2 + 3。** 三件都是「改动小、价值高」，
一轮就能同时把产品完整度（兑现忌口、减少重复填写）和 UI 观感（一屏不再亮 5 种底色）都提上去。

## 五、附：本次审查用到的量化口径

- 页面规模：wxml / wxss / js 行数、`bind*` 交互入口去重计数
- 功能面：从 wxml 的区块注释 + 用户可见文案提取
- 色彩：`app.wxss` 里 37 个变量逐个算 H/S/L；各页面 `background: var(--xxx)` 出现次数统计；
  硬编码 `#RRGGBB` 逐文件统计
- 能力核查：对「订阅消息 / 评分反馈 / 价格 / 周视图」等做全仓 grep，确认是「没有」而不是「我没看到」
