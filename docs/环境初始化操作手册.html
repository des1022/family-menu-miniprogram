一、这次到底发生了什么

「在旧电脑上从来不用弄」是因为 —— 建表这件事**只在环境第一次开通时做过一次**，之后一直沿用。 这次不一样的地方是：云环境里的 5 张表被清空了（环境被回收/重置）， 所以小程序一打开就报 -502005 Db or Table not exist，什么都存不进去。 这跟换电脑没有任何关系。重做一次即可，不会反复。

二、以后环境再被清空，怎么恢复

两步，都写成了脚本：

  1. 建集合
    # 需要小程序的 AppSecret（微信公众平台 → 开发管理 → 开发设置）
MP_APPSECRET=xxxx node tools/init-env.mjs
    脚本会自己查出缺哪些集合、只建缺的，建完再复核一遍。 也可以在 GitHub 仓库 Actions 里手动跑 init-env 流程。
  2. 设权限
    node tools/cloudbase-perm.mjs
    首次会打印一个设备码和授权链接，用微信打开 → 选 「使用微信公众平台账号登录」（专为小程序开发者，不需要腾讯云账号、不需要实名）→ 授权。 然后脚本会自动把 5 个集合全部设成所有用户可读写，并复核。

⚠️ 权限这一步千万别省。
如果集合停在默认的「仅创建者可读写」（这次查出来就是 PRIVATE）， App 表面上是好的 —— 你自己录的菜自己看得到；但家人打开是空的，采购清单也勾不动， 而且完全不会报错。安静地坏掉，是最难发现的问题。

三、为什么必须是「自定义安全规则」

云开发有四种「简易权限」，但一种都不够用 —— 关键原因：

在任何一种简易权限下，小程序端都不能修改「别人创建的」记录。

而家里用这个 App，恰好处处都要改别人的记录：

场景谁创建谁修改简易权限行不行
买菜的人勾掉已买做饭的人加的采购项买菜的人不行
撤掉别人点的一道菜点菜的人其他人不行
修改菜品 / 标常吃录入的人其他人不行
确认这顿饭（写当天所有记录）各自创建确认的人不行

所以只能写死成 {"read": true, "write": true}。它是恒真规则，还有额外好处： 用自定义规则时系统不会再自动补 _openid 查询条件， 也不会因为「查询条件没覆盖规则」而报 -502003 permission denied。
