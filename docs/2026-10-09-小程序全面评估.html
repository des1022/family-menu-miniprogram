家庭菜单小程序 · 全面评估

2026-10-09 · 评估范围：源码 49 个文件 / 7757 行 + 云端数据 + 部署链路 · 结论来自逐文件读码与云端取证（含 openid 比对）
一句话结论
  1. 能不能用：能，而且核心闭环是通的——点菜 → 采购 → 确认 → 日历留痕，家人共享也生效，这些我已经从云端数据端到端验证过。
  2. 最该补的不是功能，是「数据安全网」：这个云环境被清空过一次，家里录的菜和历史全丢了，而目前只有手动导出这一条退路。这是唯一一个可能让你真的损失东西的问题。
  3. 工程结构上欠了三笔账：没有云函数、没有自动化测试、没有错误上报。都不影响今天使用，但会让你后面每一次改动都靠「真机撞」——这三天我们撞了四次（日历没日期、分类进不去、成员重复、跑错版本）。

03 · 问题清单

A · 数据与安全（最该先看）

P0 没有自动备份，而环境已经被清空过一次

现象：5 个集合曾被整体清空，旧数据（几十道菜 + 历史记录）没有找回来。现在唯一的退路是家庭页手动点「数据备份导出」。

为什么是 P0：功能坏了能修，数据丢了修不回来。而且导出的 JSON 目前没有「导入/恢复」功能——备份出来，真要恢复还得手写代码。

建议：① GitHub Actions 加一条每周定时任务，用微信云开发 HTTP API 把 5 个集合导出成 JSON 提交到仓库（或存为 artifact）；② 补一个「从备份恢复」。两件事合起来，环境再被清空也能一键还原。

P1 集合权限是「所有用户可读写」

现象：5 个集合都是 {"read": true, "write": true}。这是当初为了「家人之间互相能改对方的数据」（买菜的人勾掉做饭的人加的采购项）才这么设的 —— 云开发的四种简易权限都做不到跨用户读写。

风险边界：目前能打开小程序的人 = 项目成员 + 体验成员白名单，所以实际暴露面有限，openid 也是随机的。但一旦上线、或把体验二维码发给外人，就等于把整个家庭数据公开可写。

建议：短期可以不动（接受这个交换），但要在书面上写清这条边界；长期如果要做严肃一点，就要引入云函数把写操作收口，权限改回「仅创建者可读写」。

P1 「我是谁」只记在本机，换客户端就得猜

现象：成员身份靠本地缓存记；PC 微信那边本地记忆不跨会话保留，所以每次打开都得重新认一次（这两天已经因此产生过 4 条重复成员）。

建议：把身份记到云端：members 上存「认领过这条成员的 openid 列表」，客户端用云函数（或临时文档探测）拿到自己的 openid 就能自动认回。一次投入，之后在任何设备都免打扰。

P2 导出有、导入无

备份文件目前只能留档，没有一键恢复入口。建议和 P0 一起做。

B · 工程结构

P1 没有云函数，等于放弃了服务端

现在做不到的事：拿自己的 openid（身份问题）、写操作的服务端校验、定时任务（自动备份）、给家人发订阅消息提醒（「今晚吃红烧肉，谁来买菜」）。

建议：先只加一个很小的 whoami 云函数（返回 openid）——它顺手解决身份问题，也把云函数这条链路打通，后面想加什么都有地方放。

P1 没有自动化测试，回归全靠真机

事实：2600 行页面逻辑 + 1700 行 utils，只有 lint.py 的静态检查兜底（它已经立功了——日历那个 bug 就是它抓出来的同类）。数据层（db.js 60+ 函数）一行测试都没有。

建议：把纯逻辑函数（食材分组、做法解析、决策器挑选、日期计算）抽出来做 node 单测 —— 这些不依赖小程序环境，成本低、回报高。顺带在 CI 里加一步跑 lint + 单测，不合格不许部署。

P1 全量拉取 + 常驻监听，数据涨上来会变慢

现象：fetchAll 每次打开把集合整表拉下来（100 条/页，最多 20 页 → 2000 条是硬上限，超出会静默截断）；getAllRecords 为了算「最近常吃」在 4 个页面各拉一次全表历史；今晚页还常驻一个 watch 实时监听。

建议：把「记录统计」在写入时增量维护（记录一条就更新菜品上的次数/最近日期），页面改成按需查；分页上限那 2000 条要么明确报错、要么真的分完。

P2 单页过大、无错误上报

tonight.js 741 行，一个文件里塞了「未点/已点 + 决策器 + 做法 + 环境引导 + 身份认领」五套状态。手机上出问题只能靠用户描述，没有错误收集（只有「数据连接自检」这一个诊断入口）。

C · 体验与产品

P1 分享能力被认证卡住，「让家人点菜」这条路没了

未认证 → 转发、分享到群都不可用。所以「让家里每人点一道」这个初衷，现在只能靠：把体验版二维码发到家庭群（一次性）+ 家人自己从「最近使用」进。海报能保存到相册再发群，是目前唯一顺畅的分享路径。

建议：把「发家庭群」这条路径做扎实（例如首页给一个「怎么让家人进来」的说明，而不是靠口头讲）；要真正恢复转发，就得走小程序认证。

P1 家里人年纪大的话，字偏小

正文字号 24–30rpx（约 12–15px），对长辈偏小。你之前把「大字号模式」列为暂缓，但它是这个产品最直接的可用性提升。

P2 没有菜图、日历只能看不能改

菜品没图时是色块 + 首字占位，不难看但缺辨识度；日历只能浏览，想撤掉某天的菜得回今晚页。另外「忌口冲突提示 / 点菜留言」你已明确暂缓。

04 · 建议的下一步（按性价比排）

#做什么为什么排在前面量级
1自动备份 + 一键恢复唯一能造成真实损失的问题；做完之后「环境被清空」这类事故就彻底不怕了小～中
2身份落库（openid 记到 members）消掉「每次开都问一次」；顺手把云函数链路打通，为后面铺路小
3CI 加质量门禁（lint + 纯逻辑单测）成本极低；这三天四次真机撞坑，一半本来是能被拦住的小
4大字号模式对长辈是刚需，改动集中在变量层小
5「怎么让家人进来」引导补上被封掉的分享路径，减少你每次口述小
6数据层瘦身（统计改增量、分页上限处理）现在不痛，但使用满一年后会痛中
7小程序认证恢复转发、支持上线；属于「要不要长期用」的决定，不是技术问题流程性

05 · 值得肯定的地方

这套东西的底子比我预想的好。原生小程序 + 云开发，零第三方依赖、零自建后端，任何一台电脑 clone 下来就能改；部署全自动（本机连开发者工具都不用装）；图标是自己渲染出来的、深浅两套主题一次做对；数据层把 60 多个操作收在一个 db.js 里，换页面不会牵一发动全身。

真正的问题不在这些，而在「出错了你看不见」——没测试、没上报、没备份。把第 1、3 两条做完，这个项目的可靠度会跳一个台阶。
